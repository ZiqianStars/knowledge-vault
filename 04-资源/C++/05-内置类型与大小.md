# 内置类型与大小（MSVC 实测值）

> 原文：[内置类型 (C++) | Microsoft Learn](https://learn.microsoft.com/zh-cn/cpp/cpp/fundamental-types-cpp?view=msvc-170)

## 一句话概括

> 一张 **MSVC 下的确切字节数表**——注意 **`long` 在 64 位 Windows 上仍然是 4 字节**，这是 Windows 与 Linux/macOS 移植时最常翻车的一条。

## 核心内容

### 一、MSVC 下各类型的存储大小（唯一的权威数字）

| 大小 | 类型 |
| --- | --- |
| **1 字节** | `bool` · `char` · `char8_t` · `unsigned char` · `signed char` · `__int8` |
| **2 字节** | `char16_t` · `__int16` · `short` · `unsigned short` · `wchar_t` · `__wchar_t` |
| **4 字节** | `char32_t` · `float` · `__int32` · `int` · `unsigned int` · `long` · `unsigned long` |
| **8 字节** | `double` · `__int64` · `long double` · `long long` · `unsigned long long` |

> **⚠️ `long` 即使是 64 位操作系统上也是 4 个字节。**
> 这是 Windows（LLP64 模型）与 Linux/macOS（LP64 模型）最关键的差异之一——后者 `long` 是 8 字节。

完整取值范围另见官方 [数据类型范围](https://learn.microsoft.com/zh-cn/cpp/cpp/data-type-ranges?view=msvc-170)。

### 二、标准只保证「相对大小」，不保证绝对值

C++ 标准施加的约束只有三条：

```
1 == sizeof(char) <= sizeof(short) <= sizeof(int) <= sizeof(long) <= sizeof(long long)
short      >= 16 位
long       >= 32 位
long long  >= 64 位
```

**所以上表的字节数是「MSVC 的实现」，不是「C++ 的定义」。** 写跨平台代码时不能依赖这些数字。

**整型的同义词组**（编译器视为同一类型，可任意排列组合）：

- `short` / `short int` / `signed short` / `signed short int`
- `long` / `long int` / `signed long` / `signed long int`
- `long long` / `long long int` / `signed long long` / `signed long long int`

即 `short unsigned` 和 `unsigned int short` 指的是同一个类型。

### 三、MSVC 特有的整数类型

| MSVC 类型 | 等价于 | 大小 |
| --- | --- | --- |
| `__int8` | `char` | 1 字节 |
| `__int16` | `short` | 2 字节 |
| `__int32` | `int` | 4 字节 |
| `__int64` | `long long` | 8 字节 |

四者都可以加 `signed` / `unsigned` 修饰。**用途就一个：宽度写死，不随平台变。**

### 四、`void`

`void` 描述值的**空集**，不能声明 `void` 类型的变量。用途只有三个：声明不返回值的函数、声明通用指针、作为强制转换目标。

被转换为 `void` 的表达式，仅限于三种上下文：表达式语句、逗号运算符的左操作数、条件运算符 `? :` 的第二或第三个操作数。

### 五、`std::nullptr_t`

`nullptr` 是类型为 `std::nullptr_t` 的**空指针常量**，可转换为任何原始指针类型。这是它与 `NULL`（本质上是 `0`）的本质区别。

### 六、字符类型——坑最多的地方

| 类型 | 用途 | MSVC 特别说明 |
| --- | --- | --- |
| `char` | 基本执行字符集编码 | **`char` 会被提升为 `int`，默认行为同 `signed char`**（带符号扩展），除非使用 [`/J`](https://learn.microsoft.com/zh-cn/cpp/build/reference/j-default-char-type-is-unsigned?view=msvc-170) 选项——此时视为 `unsigned char`，提升时无符号扩展 |
| `wchar_t` | 宽字符/多字节字符 | 默认是**原生类型**；`/Zc:wchar_t-` 可让它退回 `unsigned short` 的 typedef。2 字节 |
| `char8_t` | UTF-8 字符 | 表示方式与 `unsigned char` 相同，但**被编译器视为不同类型**。C++20 新增，需 `/std:c++20` 或更高 |
| `char16_t` | UTF-16 码元 | 编译器视为独立类型，2 字节 |
| `char32_t` | UTF-32 码元 | 编译器视为独立类型，4 字节 |

> **注意**：`char`、`signed char`、`unsigned char` 在 C++ 编译器眼里是**三种不同类型**——和 C 的直觉不一样。

字符串字面量前加 `L` 前缀表示宽字符类型。

### 七、浮点类型

采用 **IEEE-754** 表示法。标准只规定相对大小：`float` ≤ `double` ≤ `long double`（绝对大小未在标准中规定）。

> **⚠️ MSVC 特别说明：`long double` 与 `double` 的表示形式完全相同（都是 8 字节 IEEE-754），但编译器仍将它们视为两个不同类型。**

即 MSVC 下写 `long double` **得不到额外精度**——而 Linux/gcc 下它是 80 位扩展精度（16 字节对齐存储）。这是又一个跨平台数值不一致的来源。

## 我的理解

- **这张表里最贵的三行是 `long`（4 字节）、`long double`（= `double`）、`wchar_t`（2 字节）。** 三者都是 Windows 与 Linux/macOS 的实质差异点。移植代码时如果从哪里得到一个诡异的数值或截断，先怀疑这三类。
- **`char` 的符号性由实现定义，这是一个隐蔽的移植炸弹。** MSVC 默认为有符号（除非 `/J`），ARM 上的 gcc 默认是**无符号**。所以把 `char` 当「小整数」用在比较或算术里（比如 `if (c < 0)`），代码会在某些平台永远走不到分支。**`char` 要么当字符用，要么显式写 `signed char` / `unsigned char`，不要裸用。**
- **`char8_t`「表示方式相同但被编译器视为不同类型」这句很关键。** 它意味着 `std::string`(基于 `char`) 与 `std::u8string`(基于 `char8_t`) 在 C++20 之后**不能直接互操作**，需要显式转换。这是 C++20 引入 `char8_t` 时有意为之的设计——目的是让 UTF-8 字符串的类型系统自己说话，代价是老代码迁移的阵痛。
- **`long double` 在 MSVC 下等于 `double` 这一条，说明「用更宽的类型追求更精确」在 MSVC 上是无效的。** 需要更高精度时，正确做法不是换 `long double`，而是换算法（如 Kahan 求和）或引入高精度库。这是一个「换工具解决不了设计问题」的典型例子。
- **总结一下可移植写法**：跨平台代码用 `<cstdint>` 的 `int32_t` / `int64_t` / `uint8_t`，而不是 `long` 或 `__int64`。`__int64` 只在确定永远不离开 MSVC 时才用。

## 值得追问的问题

- 为什么 Windows 采用 LLP64（long 保持 4 字节）而 Linux 采用 LP64（long 扩到 8 字节）？历史原因是什么？
- `/J` 让 `char` 变成无符号——这会连带改变哪些库函数的行为（`std::string`？`printf` 的 `%c`？）
- `char8_t` 是独立类型导致 `std::string` 与 `std::u8string` 不兼容，C++20 下迁移 UTF-8 代码有哪些可行路径？
- MSVC 的 `long double` == `double`，那么依赖 80 位中间精度的数值算法移植过来会发生什么？（答案：结果可能和 gcc 编译的同一份源码不同）
