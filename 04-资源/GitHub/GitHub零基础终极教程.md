### 06:58 界面与基本概念详解

现在我们通过四种方式中的一种找到了我们自己的想要的项目，我们进入这个项目的页面。点击的时候进入这个页面，它叫做 Repository 就是仓库，里面包含了所有的资源、所有的代码等等。

大家进来之后第一反应就是有点懵：怎么这么多信息，全是英文我该怎么办？不要着急，我们一项一项地给大家解释清楚，到最后大家掌握所有给它们的基本要素和所有的知识。

首先我们看最左上角，有两个名字，一个是作者的名字，而第二个是项目的名字。其实项目的名字有很多重名，但是加上前面作者的名字，就基本上保证项目的唯一性。以后我给大家在视频里分享开源项目的时候，就会给大家前面作者的名字和后面项目的名字，这样的话用大家使用搜索引擎就能完整地定位到唯一的项目了。

接着往下看，我会看到有好几个子页面。我们在 Code 代码页面，还有 Issues 一些疑问和问题，Pull Request 这两个我们后面在我们自己看完项目的时候我会认真讲到。由于我们下载资源、使用资源这两个基本用不到，所以这里我们先暂且不讲，大家不要着急。

然后我们再往下看，World Monitor 是这个项目的名字。它这里有个 Public，Public 就是公开的，所有人都能访问、所有人都能使用和下载。有 Public 就有 Private，也就是说 GitHub 不只是用来开源我们的项目，也可以用来保留我们自己私有的项目，不给别人看，或者是给我们的协作者看，这个也是可以的，它是非常的好用，我自己的商业项目也是放到了 GitHub 上和别人一起协作的。

好的，我们接着往右看，这里出现了三个非常重要的指标。我们首先看 Watch，Watch 这个指标的意思就是监控的意思。点亮 Watch 之后，所有的项目的动态，包括有人提到任何的疑问、有新的功能被开发了等等，都会给你发通知。所以基本上 Watch 是一个项目参与者一般会点亮的这样一个指标，或者说你非常喜欢这个项目、你要知道这个项目的一切才会点亮，这个一般来说是比较少的。

第二个指标叫做 Fork，Fork 就是创建一个分支的意思。什么意思呢？我们点击 Fork 之后，会在我们自己的 GitHub 仓库里面创建一个一模一样的项目——不只是所有的源代码，还包含了所有疑问、包含所有的开发历史。我们点一下可以看到，点击之后就会来到这个页面，只不过这里的 owner 变成了我们自己，而仓库的名字还是不变的，当然你可以给它一个新的名字了。然后我们点击 Fork，等一会之后，我们就创建了这样一个一模一样的项目，只不过在我们自己的 GitHub 仓库里面。大家看到左上角所有者的名字变成了我，但是后面有个小图标，而这个 Fork 分支的图标意味着这个项目实际上我是从别人那里复制过来的，这里我们可以清晰地看清楚 Forked from，然后这是原仓库的地址了。

那 Fork 有什么作用呢？作用就是我们创建一个完全一模一样的版本，我们由此可以在这个软件目前现有的功能基础上，再进行二次的开发，添加我们自己想要的功能为自己所用；或者你添加了功能之后，还可以通过 Pull Request 来合并到原来的软件里面去，让目前的这个项目也拥有你刚才开发的功能。大家先大概地理解一下，Fork 主要是开发者用来二次开发复制这个项目用的。

也就是说，Watch 和 Fork 基本上都是用来给开发者的：你想要找我一期的动态就点亮 Watch 监控这个项目；你想要自己二次开发就点 Fork 复制整个的代码，那 AI 再进行二次开发。

还有第三个指标就是 Star，也是大家听到最多的这样一个指标。就是说我这个 GitHub 项目有多少多少个 Star。Star 就是收藏或者是点赞的意思，有两层含义：第一个就是我们点亮 Star 之后，就保存了这个项目，方便我们以后找到。比方我们现在点击 Star，可以看到这里变成 Star 字，然后我们进入到自己的 GitHub 页面，我们点击自己的头像，然后这里点击 Stars 就可以看到我们刚才收藏的项目了，我们都可以在这里找到，非常的方便。

除此之外，Star 还有另外一个作用，给我们这个项目的作者点赞，给这个项目点赞，表示支持这个项目。Star 越多，说明这个项目越受欢迎。所以大家看到自己喜欢的项目，不要吝啬点个赞。这个项目目前 World Monitor 的项目有 75000 个 Star，这是一个非常火爆的项目。顺便说一句，目前最火热的 GitHub 项目应该是龙虾 OpenClaw，现在有 38 万多的 Stars。

### 11:38 GitHub 基本工作原理

好，我们接着往下看。这里我们看到有两个英文单词，Branches 分支、Tags 标签，他们两个是非常重要的概念，我们一个一个看。

我们先看 Branches。我们点开这个下拉菜单，这里 Branches 分支里面有很多不同的分支，首先我们看到 main 主要分支，它是我们默认的分支，下面有以 fix 开头的分支，再往下拉可以看到以 feature 开头的分支。

那它到底是什么意思呢？我们来看这样一个动画：假如现在我在开发自己的开源项目，我在这个 main 也就是这个默认的主要的分支上进行开发工作。这里面每一个绿色的点都是一次提交。怎么理解提交呢？就是保存一次代码。比方说我修了一个 bug，那我提交一次就保存了这次修 bug 的代码；那么继续，我又开发了一个新的功能，我开发完之后我又提交一次，又保存了这次新功能的代码。

这样一次往前推，不论开发新功能不论修 bug，不论进行提交来保存代码，我一个人这样工作没问题。可是呢，有其他的贡献者、其他开发者也想跟我一起开发这个软件，那总不能每次他要等我开发完，我再把代码给他，他开发完再给我，我再继续开发吧？这样太浪费时间，太没效率了，对不对？我们应该能够并行开发，对不对？他开发他的，我开发我的，然后最后我们一起汇总，这才是正确的方式。

那怎么做到呢？这里它就开启了一个新的分支，一个新的 branch。然后另外一个开发者，他发现了我软件里的 bug，于是他创建了这样一个新的分支，修我登录里面的 bug。这样的话他就可以在他这个新的、叫做 fix-login 的分支上继续进行工作了，而这个分支在他创建的瞬间，就保存了我最近一个提交包含的所有修改和代码。

好，现在他开始对我的 bug 进行修复，而于是同时呢，我也没闲着对吧，我继续添加我想要的功能。我们两个分别在各自的分支上——我在 main 的分支，他在 fix-login 的分支上，都做了相应的代码修改。

现在问题来了，他把这个 bug 修完了之后，这个修复只在他自己的分支上对吧？他还想合并回来到我的 main 的分支上。这样的话，我的分支既有了我自己开发的功能，也有了他的 bug 修复，这时候他就要做一次 Pull Request，也就是 PR——我们刚才没有讲的那部分。简单来说就是让大家看看：我修了这个 bug，我能不能现在把它合并到我们的主要分支里面去？

这时候呢会出现两种情况：第一种情况，它修得很好，完全没有任何问题，那这时候我们就可以进行合并的工作，也就是 merge 刚才修的 bug 的代码合并到我们目前这个主要的分支上来，这是第一种情况。第二种情况它修得不好，有些问题，这时候我们给他建议让他继续去打磨一下自己的代码，这次我们就先拒绝不让他合并，他就需要再次进行修改自己的代码之后再次进行 PR，就是 Pull Request 再次请求进行合并。

这样的话每个人都可以自己开一个分支，在自己的分支上进行开发工作。往往来说以 fix 斜杠开头的，就是他开这个分支是为了改一个 bug；以 feat 开头的，就是他开这个分支是为了增加一个新的功能，因为 feat 是 feature 功能或者是特性的英文简写；如果是以 docs 开头的，就说明他开这个分支是为了修改一些文档。这些不是强制的规定，是一些大家默认俗成的一些规矩。

各自在各自的分支上进行工作之后呢，大家都合并到 main 上面来，最终 main 这个分支上会包含我们所有的新的功能和所有新的 bug 修复。

Tags 分支解决了怎么多个人同时开发的问题。我们开发着、开发着，往前进，我们觉得这个版本已经有新的功能、也比较稳定、bug 修复了，这时候我们就可以进行发布，给这个 commit 一个额外的固定版本的名字，比方说给最新的这个 commit 一个 Tag 标签 v2.5.23。

而这个标签永远对应了这个 commit。怎么理解呢？对于我们用户来说，我们看到它是一个固定的版本，我们可以进行下载和使用，而所有的版本都可以在 Tags 里面看到，点击不同的版本名称就回到了当前的版本的代码。以 2.5.23 为例，2 表示大的版本更新，下面的 5 表示一个功能的版本，而 23 表示修复的版本，往往是这样约定构成的。

现在大家就明白什么是分支、什么是 Tag 标签了。

除了 README 文件之外，还有一个特别重要的概念，就是开源软件的许可证。也就是说，开源软件和开源软件之间的开放程度也有区别。比方说我们这里点击 License，其实就是 Apache 这个许可证。平常开源圈我们都知道龙虾项目 OpenClaw，我们点击它的 license 看它的证书，它就是 MIT 证书。

不同的证书之间有什么区别呢？大家可以看到这个网页，给大家说明了 7 种常见的开源许可证之间的区别，从左到右越来越严格，我们一个一个讲。

首先 MIT 证书，这可能是大家看到最常见的一种证书了。如果这个软件是 MIT 证书，意味着你可以把这个开源软件拿过来做任何的修改，然后把它闭源变成你自己的商业软件都没有任何的限制，只不过你要保留原来开源软件的版权声明。

再往右 BSD-3-Clause 这个许可证也是非常常见的。相比 MIT 它更加进一步规定了：这个开源软件做成商业软件闭源的时候，不可以用原作者来对你的商业软件进行背书和宣传。

再往右第三个 Apache 2.0，再严格一点。你还是可以把开源软件进行闭源然后进行商用，只不过在 BSD 的基础上，你还需要把我们开源软件的专利给讲清楚。总体来说 MIT、BSD-3-Clause、Apache 2.0 都是非常宽松的，看到这三个证书就意味着你可以放心地把开源项目拿过来进行修改，然后把它进行商用，没有任何问题。

好的，现在我们接下来往右边看，这四个证书限制就变得多一点了。首先就是 MPL 2.0 证书，这个证书就规定了：如果你修改了开源软件的某一个文件，这个文件你后面也必须要开源才行，不可以闭源。

第二个 LGPL 3.0 这个证书，只要你对开源项目进行了任何的修改，那么接下来你也必须开源你修改的项目，而且是必须要用 LGPL 继承同样的证书。

第三个证书 GPL 3.0 证书，就是说我们在用这个开源软件放到我们的软件里面的时候，你再把这个软件给到你的用户的时候，你必须要提供开源软件部分的完整源代码。

那再往后 AGPL 3.0 证书，就是我们刚才看到的那个 World Monitor 它用的证书，它可能更加严格一些。就是你用了我这个开源软件做你自己的软件，就算你的软件不是直接给你的用户，而是把它做成一个在线的软件，大家可以登录可以使用，就算是这种情况下，你也必须要让任何在网上使用你软件的用户给他这个项目的源代码。

看到这四个呢，从 MPL、LGPL、GPL 到 AGPL，看到这四个证书你大概就意味着这个开源项目对商业化可能有比较严格的规定，这里我需要注意一下。

### 21:26 4 种使用 GitHub 项目的方式

前面通过 README 我们知道了这个项目是干什么的，通过 License 证书或者是许可证，我们知道了能不能使用它以及能不能修改它，现在就是最实际的问题：怎么把这个项目下载并且真正使用起来。

GitHub 上有常见的四种方式，分别是发布 Release、下载 Zip、Clone 和 Fork，也就是分支——刚才我们刚讲过。他们适合的人和用途完全不同，我们现在一个一个来讲。

首先是 Release，刚才我们已经提到了。在项目页面我们往下拉，在右边我们可以看到这边有 Releases，点击最新的版本就可以进入到它下载发布的页面，往下拉就会看到有不同操作系统的安装包：你是 Mac、你是 Windows、你是 Linux，下载对应后缀的安装包就可以。比方说你是 Windows 就下载 EXE，你是苹果电脑就下载 DMG，下载下来的就是对应的安装包，双击即可安装，跟安装其他任何软件都一样。

一句话总结：Release 就是下载作者已经做好的成品软件，你只是想使用这个软件、不想要二次开发的话，就可以直接下载 Release 里面的安装包。

Release 之外的第二种下载项目的方法，点击这里的 Code 下拉，我们可以看到有一个 Download ZIP，这里我们点击，它就会把整个项目的源代码打包进行下载到我们自己的本地电脑。下载好的压缩包双击解压，打开里面就是我们整个项目的源代码，跟我们在这里看到的是一模一样的。通过压缩包我们下载的直接就是源代码，适合你分析它的代码是怎么样的，通常不能像安装包一样双击直接安装运行了。

第三种下载和使用这个项目的方法是 Clone。Clone 这里我们还是点击这边的 Code，我们这里看到有 Clone 对吧？然后下面给我们一个地址，我们复制这个地址。你是 Mac 电脑就在 APP 里面搜索终端然后打开；如果你是 Windows 电脑就搜索 PowerShell，然后我们打上 git clone 粘贴刚才复制的地址就可以。

你可能说：好麻烦，为了在终端操作。现在有了 AI，我们可以不这么操作——随便打开一个大家用的熟悉的智能体，这里我们可以直接给我们的智能体告诉他：帮我克隆这个项目到本地，然后复制刚才的地址，回车，等一会之后 AI 就帮我们把原项目克隆到了本地。

那么相比下载安装包到本地来保存一个代码，克隆不仅仅是下载了原文件，而且在电脑上建立一个真正的本地 Git 仓库。怎么理解呢？其实很简单：除了原文件之外，它还包含了 Git 的提交历史，就是你能看到什么时间开发了什么功能、修改了什么 bug，以及各个分支的历史。还记得我们刚才讲的分支吗？那么以后原代码在 GitHub 上如果有任何的改变，你也可以随时通过 git pull 这个命令从原仓库拉取新的提交。当然你也不需要自己在终端操作了，你可以告诉 AI：帮我看看我们项目的源代码有没有更新，有的话 pull 一下，pull 就是拉的意思，就是把我们远程的最新的代码拉到本地，让本地也保持更新。

这是 git clone。大家可以看到 git clone 非常方便你把源代码放到本地之后，进行二次开发。比方说你很喜欢这个项目，但是你想要把 UI 改一下，就是这个界面的元素和这个风格改一下，为自己所用，那你就可以 git clone 这个项目到自己的本地，然后让 AI 进行一些二次的开发工作。

这是第三种方法。

第四种方法 Fork，这个其实我们也讲过了对吧，就是这个按钮。那么相比于 clone 和下载压缩包，Fork 不是把源代码下到本地的电脑，而是在你自己的 GitHub 账号中创建一个项目完全一模一样的副本，把这个项目克隆到自己的仓库里面去，主要用于你想要修改并且参与开源项目、为开源项目做贡献。

比方刚才我们已经操作了，点一下 Fork，我们就在自己的仓库创建了这样一个一模一样的项目。那我们为什么需要 Fork 来参与到我们开源项目的贡献和开发当中呢？因为通常没有权限直接去修改别人的仓库——原作者是 kaola73 对不对，就是他的仓库。但是我们现在通过 Fork，原代码放到了我们自己的仓库。我们接下来可以克隆我们自己的仓库到本地，进行任何用 AI 来开发。本地开发完之后，再把自己的修改推到我们自己远程的仓库，就是我们看到这个项目之中。然后这里我们可以做一个 Pull Request——假设我们现在有了修改，我们现在的自己仓库里的项目跟远程的原作者的项目已经不一样了，这时候我们可以点击 Pull Request → New Pull Request，把我们的修改请求合并到原项目当中。可以看到这个方向：我们自己仓库里的项目，把它合并到原作者项目里面去。当然现在我没有任何的改动，所以它会检测任何区别。整个过程大家不用担心，你可以完全通过让 AI 对话来进行，让它帮你进行 Pull Request 也就是 PR，把你的修改请求到开源项目之中。

现在我们总结下四种下载和使用开源项目的方式：第一种 Release 下载的是成品的安装包，只适合那些想使用但不想参与开发的人；第二种下载压缩包是为了临时查看文件，因为里面包含所有的源代码；第三种克隆是适合开发和拉取更新，方便自己做二次的开发；第四种 Fork 在云端创建一个一模一样的副本，适合为这个开源项目进行修改并且贡献的那些开发者。

简单来说，按照你的目的不同：只是想要安装软件，就在 Release 下载安装包；这是想要看看里面的源文件，就下载压缩包就可以了；想要长期的开发和更新，就使用 git clone 把源代码拉到自己的本地；想要修改并且贡献这个开源项目，就用 Fork 创建一个副本到自己的云端仓库里面去。

不过大家可以看到右边 Release 这里没有任何正式发布的版本，现在我们就可以发布一个正式的版本。回到与 AI 的对话框，我们告诉 AI：检查当前的项目是否适合发布 v0.1.0 第一个正式版本，如果合适的话，写一个简洁的发布说明，然后创建并推送第一个标签、第一个正式版本。

好的，我们的第一个正式版本已经发布了。我们去 GitHub 上看一下，可以看到刷新一下网页，我们右边的 Release 有了我们第一个版本。我们点进去到了发布页，说了当前的功能，然后可以打包下载我们现在的源代码——当然我们现在没有安装包了，因为这是个 skill，所以打包下载的是 ZIP 源代码了，所有人都可以在这里下载。

我们这个现在版本的 skill 为自己所用。到现在为止，我们的第一个开源项目就创建成功了，我们也发布了第一个版本。

下面我们简单讲一下如何维护。这里我以我自己的开源项目为例。我们在分享自己开源项目之后，很多朋友会发现我们这个项目里面还有可能多多少少的存在一些 bug 和问题，这时候他就可以在这个 Issues 这里进行留言。Open 就是目前公开还没有解决的问题，Close 就是我们已经解决的问题。看到我有 26 个问题没有解决，41 个问题已经解决了。比方说这个朋友他就说，他在使用这个开源软件的时候，发现评价界面里面会出现乱码的情况，这个时候我们就可以针对这个问题进行探查和修 bug。这里我们可以给他回复，问他具体操作系统等等环境的各方面的问题，等确认好之后我们可以把这个问题给到 AI 让 AI 来修复这个问题。我们的 AI 已经连到了 GitHub 的 CLI，它能操作我们的 GitHub 获取 GitHub 相关信息，我就可以告诉它：帮我看看有没有新的 issue 需不需要修复。当然我这个新的开源项目我们刚开源还没有人提出问题对吧，它这里答案肯定是没有的。不过大家可以让 AI 帮助自己解决 issue。

除了 issue 之外我们还有 Pull Request。之前我们讲过 Pull Request 对吧，就是我们想要贡献给别人的开源项目，我们就 Fork 一下这个开源项目，自己改了之后，然后做一个 Pull Request，希望把我们的改动汇入到原来的原始项目之中。这些就是一些开发者朋友，他用了我的软件，然后给我做了一些开发，或者修 bug，或者开发的新功能，希望把他们直接修改也汇入到我的主要的分支里面去。可以看到有 11 个 open 就是 11 个我还没有解决的问题，29 个已经关闭的、已经解决的问题。你可以让 AI 回到 AI 对话界面，让它帮助你判断有哪些 Pull Request 的、有哪些值得我们汇入到当前的代码里面去。
