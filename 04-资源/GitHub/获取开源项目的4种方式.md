# 获取开源项目的4种方式

> 原视频：[GitHub 零基础终极教程](https://v.douyin.com/QX-OjYMAQk4/) · 抖音 · 37分30秒 · UP：木子不写代码

## 一句话概括

> Release / Zip / Clone / Fork 四种方式的区别不在操作难度，而在**你的意图**：只想用、只想看源码、要长期开发、还是要贡献回去。选错方式返工成本很高——用 Zip 下载后再想 `git pull` 就接不上了。

## 核心内容

### 前提：先确认能不能用

原片在讲下载之前先补了一句：

> 「前面通过 README 我们知道了这个项目是干什么的，通过 License 证书或者是许可证，我们知道了能不能使用它以及能不能修改它，现在就是最实际的问题：怎么把这个项目下载并且真正使用起来」

**顺序不能颠倒。** 先看[[开源许可证]]，再下载。

### 方式一：Release —— 只想用软件

![[获取开源项目的4种方式-Release.jpg]]

*视频 22:20 —— 仓库页右侧 Releases 区域，向下滚动可见按操作系统分类的安装包列表。*

项目页右侧 → Releases → 点最新版本 → 往下拉，按系统下载对应安装包：

| 系统 | 安装包格式 |
| --- | --- |
| Windows | `.exe` |
| macOS | `.dmg` |
| Linux | 对应包 |

**双击即可安装，和装任何普通软件一样。**

> 一句话总结：Release 就是下载作者已经做好的成品软件，你只是想使用这个软件、不想二次开发，直接下载安装包。

### 方式二：下载 Zip —— 只想看源码

![[获取开源项目的4种方式-Zip下载.jpg]]

*视频 23:30 —— Code 下拉菜单里的 Download ZIP 选项。*

Code 按钮 → 下拉 → Download ZIP。整个项目的源代码打包下载到本地，解压即可看到完整源码。

**关键限制原片点出来了**：

> 「通常不能像安装包一样双击直接安装运行了」

**Zip 是源码快照，没有 Git 历史。** 后果是：
- 不能 `git pull` 拉取后续更新
- 不能看到提交历史和分支
- 不能方便地提 PR 贡献回去

**适合临时读代码、做分析、研究实现。**

### 方式三：git clone —— 要长期开发

![[获取开源项目的4种方式-Fork贡献.jpg]]

*视频 25:40 —— 左侧标注「下载使用开源项目：4. fork」，背景是仓库页的 Fork 按钮位置。*

Code → Clone → 复制那个地址：

```bash
# macOS：打开「终端」
# Windows：打开 PowerShell
git clone <粘贴地址>
```

**Clone 和 Zip 的本质区别**（原片讲得很准）：

> 「克隆不仅仅是下载了原文件，而且在电脑上建立一个真正的本地 Git 仓库……除了原文件之外，它还包含了 Git 的提交历史，就是你能看到什么时间开发了什么功能、修改了什么 bug，以及各个分支的历史」

因此 Clone 之后：
- 可以 `git pull` 随时同步远程最新提交
- 可以查看完整历史
- 可以自由改（二次开发）

**适用场景**：想改 UI、改功能、做二次开发。

### 原片的 AI 时代做法

原片特别强调不必手打命令：

> 「现在有了 AI，我们可以不这么操作——随便打开一个大家用的熟悉的智能体，直接告诉它：帮我克隆这个项目到本地」

同步更新也一样：

> 「你可以告诉 AI：帮我看看我们项目的源代码有没有更新，有的话 pull 一下」

**用 AI 替代终端操作**，这是这期教程与其它 GitHub 教程最大的路线差异。

### 方式四：Fork —— 要参与贡献

点 Fork → 在**自己账号下**创建一份完全一样的副本（源码 + issue + 提交历史）。

**注意 Fork 不下载到本地**——副本在你的云端仓库里。

为什么要用 Fork 而不是直接改？原片的解释：

> 「因为通常没有权限直接去修改别人的仓库——原作者是 kaola73 对不对，就是他的仓库。但是我们现在通过 Fork，原代码放到了我们自己的仓库」

完整工作流：

```
Fork（原项目 → 我的云端副本）
  ↓
Clone（我的副本 → 本地）
  ↓
本地用 AI 开发
  ↓
push（本地 → 我的远程副本）
  ↓
Pull Request（我的副本 → 原项目，请求合并）
```

**整条链路可以全程用 AI 对话完成**，原片说「你可以完全通过让 AI 对话来进行，让它帮你进行 Pull Request」。

### 四种方式速查

| 方式 | 得到什么 | 适用意图 | 能否同步更新 | 能否贡献回去 |
| --- | --- | --- | --- | --- |
| **Release** | 成品安装包 | 只想用 | 看作者更新后重新下 | 否 |
| **Zip** | 源码快照 | 只想读代码 | **否** | 否 |
| **git clone** | 源码 + 完整 Git 历史 | 长期开发、二次开发 | 是（`git pull`） | 间接（先 Fork） |
| **Fork** | 自己账号下的完整副本 | 贡献回原项目 | 是 | **是（直接提 PR）** |

## 关键摘录

| 原文 | 我的想法 |
| --- | --- |
| 「通过压缩包我们下载的直接就是源代码，适合你分析它的代码是怎么样的，通常不能像安装包一样双击直接安装运行了」 | Zip 的定位是「读」，不是「用」 |
| 「克隆不仅仅是下载了原文件，而且在电脑上建立一个真正的本地 Git 仓库」 | 一句话说清 clone 和 zip 的差异 |
| 「而这个 Fork 分支的图标意味着这个项目实际上我是从别人那里复制过来的」 | Fork 在 UI 上有明确标记，避免误认为是原创项目 |
| 「总不能每次他要等我开发完，我再把代码给他……这样太浪费时间，太没效率了」 | 协作成本正是分支机制存在的理由 |

## 我的理解

- **这四种方式的分野是「意图」而不是「操作难度」。** 初学者的常见错误是「我不知道哪个好，就用最复杂的」——去 Clone 了一个只想装来用的软件，或者用 Zip 下载了一个想长期跟的项目。**先问自己「我要拿它干什么」，答案就出来了。**
- **Zip 的不可逆性是最值得强调的。** 用 Zip 下载后想切换到 Clone，只能删了重来（重新 clone + 重新看代码历史）。这是四种方式里唯一有「选错即返工成本高」特征的。
- **Fork 是给「参与者」准备的，不是给「用户」准备的。** 只想用软件的人完全不需要碰 Fork——Fork 是在自己名下维护一个副本，后续要自己维护 PR 沟通成本。
- **原片把 AI 编排嵌进了每一步**，这让整套流程对零基础友好得多：clone、pull、push、提 PR 都可以一句话交给智能体。**但有个隐含代价**——出问题时你得知道 AI 到底做了什么，否则排查会非常困难。
- **Release 里也有源码包**（GitHub 自动生成的 Source code (zip) / tar.gz），原片没强调这点。这在只有 Release 没有 Clone 条件时是有用的备份。

## 可行动的结论

- [ ] 养成先问意图再选方式的习惯：用 → Release；读 → Zip；改 → Clone；贡献 → Fork
- [ ] 需要长期跟的项目，一律 Clone，别用 Zip
- [ ] 试一次「让 AI 执行 git clone 和 git pull」，观察它做了什么
