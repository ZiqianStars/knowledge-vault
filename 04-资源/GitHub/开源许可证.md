# 开源许可证

> 原视频：[GitHub 零基础终极教程](https://v.douyin.com/QX-OjYMAQk4/) · 抖音 · 37分30秒 · UP：木子不写代码

## 一句话概括

> 许可证决定了**你能不能把开源代码闭源进商业产品**。MIT / BSD-3-Clause / Apache-2.0 宽松到可以闭源商用；MPL / LGPL / GPL / AGPL 有传染性，AGPL 甚至管到 SaaS。

## 核心内容

### 为什么要看许可证

原片的逻辑链很清晰：

1. 看 README → 知道这个项目**是干什么的**
2. 看 License → 知道**能不能使用它、能不能修改它**
3. 然后才是「怎么下载、怎么跑起来」

**许可证是使用前的必查项，不是出事后再查的东西。**

### 宽松三兄弟（可闭源商用）

![[开源许可证-七种许可证对照表.jpg]]

*视频 19:52 —— GitHub 官方 7 种许可证对照表，左侧 MIT / BSD-3-Clause / Apache-2.0 为宽松档，右侧 MPL / LGPL / GPL 为严格档。*

| 许可证 | 核心条款 | 额外限制 |
| --- | --- | --- |
| **MIT** | 可任意修改、可闭源成自己的商业软件 | 只需保留原版权声明 |
| **BSD-3-Clause** | 同 MIT | **不可用原作者为你的商业软件做背书宣传** |
| **Apache-2.0** | 同 BSD | **还需把开源软件涉及的专利讲清楚**（专利授权条款） |

**原片的总结**：

> 「总体来说 MIT、BSD-3-Clause、Apache 2.0 都是非常宽松的，看到这三个证书就意味着你可以放心地把开源项目拿过来进行修改，然后把它进行商用，没有任何问题。」

**共同点是：你的商业产品可以是闭源的。** 唯一的义务是保留版权声明（BSD 追加不得背书，Apache 追加专利条款）。

### 严格四种（有传染性）

![[开源许可证-严格四种的限制.jpg]]

*视频 21:08 —— 左半屏是 GitHub 的「有 LICENSE 许可证」说明页与许可证名称列，右半屏标注「开源修改的这个项目」。*

| 许可证 | 传染范围 | 关键条款 |
| --- | --- | --- |
| **MPL-2.0** | 文件级 | 改动了某个**文件**，那个文件必须继续开源，不能闭源 |
| **LGPL-3.0** | 库级 | 任何修改都必须开源，且**必须用 LGPL 继承同样的证书** |
| **GPL-3.0** | 产品级 | 把软件给用户时，**必须提供开源部分的完整源代码** |
| **AGPL-3.0** | **网络服务级** | 就算做成在线 SaaS、用户登录使用，**也必须让用户拿到源代码** |

### AGPL 是 SaaS 公司的雷

原片对 AGPL 的解释值得单独拎出来：

> 「你用了我这个开源软件做你自己的软件，就算你的软件不是直接给你的用户，而是把它做成一个在线的软件，大家可以登录可以使用，就算是这种情况下，你也必须要让任何在网上使用你软件的用户给他这个项目的源代码」

**触发条件是「通过网络提供服务」，而不是「分发软件」。** 很多公司以为自己的服务不涉及「分发」就没事，AGPL 恰恰堵的就是这条路。

## 关键摘录

| 原文 | 我的想法 |
| --- | --- |
| 「MIT 意味着你可以把这个开源软件拿过来做任何的修改，然后把它闭源变成你自己的商业软件都没有任何的限制，只不过你要保留原来开源软件的版权声明」 | MIT 之所以是最常见许可证，就是因为它对使用者最宽松 |
| 「相比 MIT 它更加进一步规定了：不可以用原作者来对你的商业软件进行背书和宣传」 | BSD 加的是「不许蹭作者名气」，这一条很多人会忽略 |
| 「你还需要把我们开源软件的专利给讲清楚」 | Apache-2.0 的专利条款是其与 BSD 的核心差异 |
| 「只要你对开源项目进行了任何的修改，那么接下来你也必须开源你修改的项目，而且是必须要用 LGPL 继承同样的证书」 | 「必须用同样的证书」是 copyleft 的本质，不只是"要开源" |
| 「就算你的软件不是直接给你的用户，而是把它做成一个在线的软件……也必须要让任何在网上使用你软件的用户给他这个项目的源代码」 | AGPL 管的是网络服务，这是它与其他所有许可证的分水岭 |

## 我的理解

- **这个阶梯的划分标准只有一条：你的产品能不能闭源。** MIT 档可以，MPL 档要按文件开洞，GPL 档整个产品都得开源，AGPL 档连不分发代码的在线服务都算。**记住这一条，七种许可证的差异就都能推出去了**，不用背。
- **MPL 是最容易被误判的一个。** 它常被和 LGPL 混为一谈，但它是**文件级** copyleft：只改了 a.py，a.py 要开源，其它文件不受影响。这个粒度差异在商业项目里影响很大。
- **AGPL 的条款对创业公司的杀伤力被普遍低估。** 「我们只是提供 SaaS，没分发代码」是最常见的错误认知。AGPL 就是专门堵这个洞的。
- **原片用了「从左到右越来越严格」这个单一维度来教学，这对零基础是够用的**，但严格来说不是完全线性的——MPL 的文件级粒度比 LGPL 的库级更细。教学上这么讲没问题，实际判断时要看**具体条款**。
- **实际工作中的做法**：这不是靠背能解决的。真正稳妥的做法是——**商用前把项目的 LICENSE 文件拉下来读一遍，必要时让法务看一眼**。原片给的是判断框架，不是法律意见。

## 可行动的结论

- [ ] 把自己项目里用到的所有开源依赖列个表，逐个标注许可证类型
- [ ] 划一条线：MIT / BSD / Apache 可以闭源商用，其余四个先问法务
- [ ] 如果用了 AGPL 项目且提供在线服务，立刻复查——这是最紧急的一类
- [ ] 开源自己的项目时，选 MIT（原片示范）或按实际意图选，但**必须选一个并写清楚**
