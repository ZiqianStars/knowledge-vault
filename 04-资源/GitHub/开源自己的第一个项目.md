# 开源自己的第一个项目

> 原视频：[GitHub 零基础终极教程](https://v.douyin.com/QX-OjYMAQk4/) · 抖音 · 37分30秒 · UP：木子不写代码

## 一句话概括

> 从一个空文件夹到公开的 v0.1.0 Release，八步：写 README → 加许可证 → **安全检查** → 装 Git → 初始化仓库并首次提交 → 装 GitHub CLI 并登录 → 推送 → 打标签发 Release。**全程可以让 AI 代劳。**

## 核心内容

### 完整流程

![[开源自己的第一个项目-四个步骤.jpg]]

*视频 28:00 —— 章节标题「开源第一个项目：1. 创建文件夹」，画面是作者桌面演示环境。*

```
1. 建空文件夹 → 2. 用 AI 编程智能体开发项目
3. 写 README（AI 写，人审）
4. 加许可证（示范用 MIT）
5. 安全检查  ← 最容易跳过，也最容易出事
6. 检查/安装 Git → git init + 默认分支 main + 首次 commit
7. 安装 GitHub CLI → gh auth login → 推送（可见性 public）
8. 打 Tag 发 Release（v0.1.0）
```

**第 5 步之后才是 Git 相关操作。** 原片的顺序是刻意的：内容和合规先就绪，再进版本控制。

### README 必备清单

![[开源自己的第一个项目-README必备清单.jpg]]

*视频 30:05 —— 幻灯片列出 README 应包含的五项，末行强调「README 必须与项目实际情况一致」。*

| 必含内容 | 说明 |
| --- | --- |
| 项目解决什么问题 | 一句话说清价值 |
| 主要功能 | 功能列表 + 预览截图 |
| 安装方法 | 让别人能跑起来 |
| 使用方法 | 具体怎么用 |
| 输入输出示例 | 最直观的效果展示 |

**原片的强调点**：「README 必须与项目实际情况一致。」写的时候让 AI 生成，人来审核——AI 容易写出漂亮但与实际不符的说明。

### 第 5 步：安全检查（最关键）

原片让 AI 检查这些项：

> 「检查整个项目是否存在有密码或者 token 的泄露、个人的隐私、本地的绝对路径、临时文件、垃圾文件，以及不公开的内容，保证我们公开的项目里面没有任何隐私和不该公开的内容」

**清单**：
- 密码 / token 泄露
- 个人隐私信息
- **本地绝对路径**（如 `/Users/xxx/...`，会暴露用户名和目录结构）
- 临时文件、垃圾文件
- 不该公开的内容

> 原片的提醒：「这个 skill 其实没什么，但是要发布到 Git 仓库的话，大家就不要忘记做最后这一步。」

**这一步是从「能跑」到「能公开」之间真正容易出事的一步。** 其它教程通常会跳过。

### 第 6 步：Git 初始化与首次提交

先检查本机有没有装 Git，没装就让 AI 识别操作系统并安装。然后：

```bash
git init
# 默认分支设为 main
git add .
git commit -m "..."
```

原片的解释很朴素：「这些提交就是之前我们说的 commit，大家现在可以简单认为我们保存一下代码。」

**注意此时提交只在本地**，还没公开。

### 第 7 步：GitHub CLI 与登录

原片建议装 GitHub CLI（CLI = 命令行），专门用来让 AI 操作 GitHub。

```bash
gh auth login
# 选择：Login with a web browser
```

原片演示了完整的浏览器登录流程，并说明如果 AI 报告已登录可以直接跳过。

### 第 8 步：推送与发版

推送时告诉 AI：新建仓库名、可见性设为 **public**、推送分支是 **main**。

原片强调可见性这一步：

> 「告诉它可见性是 public，也就是所有人都可见，这是个开源项目」

**发布首个版本**：告诉 AI 检查项目是否适合发布 v0.1.0，写简洁发布说明，创建并推送第一个 Tag。

发布后 GitHub 页面右侧会出现 Release 条目，**自动附上源码包**（Source code zip/tar.gz）供人下载。**没有安装包是正常的**——因为这是 skill 类项目，不是可执行软件。

### 第 9 步：发布之后的维护

原片用自己的开源项目举例：

| 位置 | 含义 |
| --- | --- |
| **Issues → Open** | 尚未解决的问题（他的项目 26 个） |
| **Issues → Closed** | 已解决的问题（他的项目 41 个） |
| **Pull Requests → Open** | 待评审的贡献（他的项目 11 个） |
| **Pull Requests → Closed** | 已合入的贡献（他的项目 29 个） |

**Issue 的处理流程**：用户留言说界面出现乱码 → 维护者回复询问操作系统等环境信息 → 定位问题 → 把问题交给 AI 修复。

**因为 AI 已经连上 GitHub CLI，能直接获取仓库信息**，所以「帮我看看有没有新的 issue 需不需要修复」这类指令可以直接交出去。

## 我的理解

- **原片最值得学的不是 Git 命令，是这套流程的完整性。** 命令可以查，流程顺序漏了就真出事。README → 许可证 → 安全检查 → 这三步是「内容合规」，很多教程直接从 git init 开始，跳过了最要紧的部分。
- **安全检查是被低估的一步。** `git commit -a` 会把整个目录打包进历史——**一旦 push 到公开仓库，泄露的密码就进了 git 历史，改掉工作区文件也删不掉**（需要 filter-repo 之类工具重写历史）。所以这一步必须在 commit 之前做。原片的顺序是对的。
- **「让 AI 代劳所有终端操作」是这期的方法论内核。** 原片不是教 git 命令行，是教「怎么把 git 流程描述给 AI」。这跟传统的 Git 教程是两条路。对已经习惯用智能体的人，这套流程可以直接迁移。
- **但要留个心眼**：让 AI 执行 push、创建公开仓库这类**对外动作**，等于授权了对外发布。原片演示时是本地环境。实际用在自己的项目上时，push 前应该自己确认一遍要提交的文件清单（`git status`），以及**仓库可见性是 public 还是 private**。
- **原片没讲 .gitignore**——但这是安全检查的隐含前提。不配 .gitignore，`node_modules`、`.env`、构建产物都会进版本库。实操时必须补上。

## 可行动的结论

- [ ] 开源前必做：安全检查（密码/token/绝对路径/临时文件）+ 配 .gitignore
- [ ] README 五件套写全，且必须与实际行为一致
- [ ] 想清楚仓库可见性：public 还是 private，推送前确认
- [ ] 走一遍完整流程：git init → 首次 commit → gh auth login → push → 打 v0.1.0 标签发 Release
- [ ] 把 `gh` CLI 装好并登录，为后续让 AI 维护 issue / PR 做准备
